# Approved Drive OAuth design — P3-003

Status: design complete; live authorization, deployment and refresh testing NOT performed. Architecture approved by owner: direct Kodi add-on with maintainer-operated relay. Source/flow evidence is pinned in `migration/google-drive/source-lock.json` and summarized in `docs/google-drive.md`. A new Drive grant is needed when configuring this previously absent integration; existing other add-on accounts stay in the private migration bundle.

## Trust and scope

Use only the current HTTPS sign-in endpoint `https://drive.signinserver.com` and the provider's Google consent pages. Verify requested consent remains `https://www.googleapis.com/auth/drive.readonly`. This is a restricted scope permitting reads/downloads across the account, not merely a UI-selected media folder. `drive.file` is narrower but does not automatically grant access to an existing 5 TB library. UI folder restrictions do not narrow the OAuth token's authority. Stop if unexpected write scopes, endpoints or permissions appear; seek owner review rather than expanding access silently. See [Google scope definitions](https://developers.google.com/workspace/drive/api/guides/api-specific-auth).

The maintainer's relay handles the authorization-code exchange and receives refresh-token requests. The upstream design uses PKCE, short codes and a random pickup secret; it reports transient in-memory token retention for up to three minutes and no token logging/database. This is a source/documentation claim, not an audit of the deployed public service. Upstream also describes aggregate usage/version/country metrics; do not promise zero metadata collection. Media requests go to Drive through Kodi's local download path, not through the sign-in relay. The owner has explicitly accepted this relay trust boundary; a different/self-hosted relay needs another decision.

Sign-in pairing uses network/IP checks. A Safari/Kodi network change, VPN or iCloud privacy relay may prevent pairing; keep the context consistent and diagnose without posting login codes, QR images or tokens. No Google password is collected by this project or committed to Git.

## Private state and lifecycle

The add-on uses private writable Kodi addon_data/account storage (the common code uses an accounts database); do not claim OS-keychain or encrypted-at-rest protection. Exact target container and permissions must be verified in Phase 4. Keep account databases, refresh/access tokens, exported private STRM links and debug logs outside Git, IPA resources and the public configuration. Raw screenshots containing codes/accounts/media stay private. Keep a private recovery copy before account migration and retain source/target add-on schema/version information. Do not bulk-copy another account or introduce hardcoded user/account identifiers.

On expiry, the upstream client requests refreshed access through the relay. Test a successful refresh, provider rejection and relay/network failure without exposing responses. Distinguish transient failures from `invalid_grant`/revoked access; use bounded recovery rather than endless repeated login prompts. The pinned OAuth wrapper retains its request retry budget for 503 but stops this call on other HTTP errors such as 429; it does not promise automatic Retry-After scheduling for every quota case. Wait/back off deliberately before retrying rate-limit failures; do not retry indefinitely. For other transient errors, respect the actual client retry budget and request new consent only if required. [Google's OAuth lifecycle](https://developers.google.com/identity/protocols/oauth2) documents expiry/revocation and seven-day refresh-token expiry for many external apps in Testing status. Repeated login needs may therefore reflect OAuth project configuration rather than a lost Kodi profile.

Account removal may optionally revoke provider access. Upstream 1.6.8/common 1.5.10+ warns this can sign out other Kodi devices using the grant. Require deliberate owner choice before revocation; do not treat revocation as a routine refresh fix. Keep the original private backup and do not revoke existing other integrations.

## Validation and readiness gates

Validate endpoint/scope/version pins statically, test mocked sign-in cancellation and failed grants, storage safety, redaction and explicit revocation behavior. The original local preflight passed those mocks but failed eight streaming tests because local sockets were denied. Approved CI now passed all 42 tests at the same source pin; the old failure remains recorded. Additional pinned-source tests confirm expired-token refresh, fresh-token reuse, failed-refresh state retention, bounded 503 retry budget, 429 stop behavior and mocked library-indexed resume. No personal grant or real video is needed for those host tests.

After host integration checks pass, validate actual Google consent, refresh/revocation recovery, account isolation, video startup, repeated range seeking, subtitles, resume and background/foreground behavior on the real iPhone during Phase 4. Use synthetic/publicly licensed test media privately; do not upload or modify the owner's media to make a test pass.
